# Repository Management

A repository is operated, not just filled. This is the surface that decides who can change what, what
a change must satisfy, and how the project stays legible a year later.

## Ownership and protection

- `CODEOWNERS` for the paths where a mistake is expensive (auth, payments, migrations, CI, infra).
- Protect the default branch in the repository settings, not in the team's memory: no direct pushes,
  at least one review, required status checks, linear history, no force-push, no deletion.
- Require review from code owners on their paths; require a fresh approval after new commits.
- Keep an explicit list of maintainers with admin rights; admin bypass is an incident, not a habit.
- For a project with co-maintainers, agree who merges and how disagreements are resolved in writing.
- Archive instead of abandoning: an archived repository with a README pointer costs nothing and stops
  people depending on dead code.

## Templates that make review cheaper

- Issue template with: symptom, environment, reproduction, expected versus actual, and acceptance
  criteria containing the commands that will prove it. A ticket an agent cannot verify is not ready.
- Pull request template with: why, what, evidence, test plan, what was NOT run, risk, rollback.
- Both templates ask for the same evidence the pipeline produces, so the review and the CI agree.
- A `CONTRIBUTING.md` that answers "where does my change go" for the three or four common cases, and a
  `SECURITY.md` that routes vulnerabilities privately.
- A `CHANGELOG.md` maintained by the release process, not by hand at the last minute.

## Labels and triage

- Type labels (`bug`, `feature`, `docs`, `chore`), status labels (`needs-triage`, `needs-info`,
  `ready-for-agent`, `ready-for-human`, `wontfix`), and a size signal applied automatically.
- One type label per issue, so querying "all bugs" is not a search for synonyms.
- A stale policy with a real deadline and an action, not a bot that closes things silently.
- Triage is a scheduled act: every open issue has an owner, a status and a next action, or it is closed.

## Automation worth running

| Automation | Rule |
| --- | --- |
| Dependency updates (Dependabot/Renovate) | Grouped by ecosystem, one PR per group, auto-merge allowed only for patch updates with a green matrix |
| Secret scanning | Enabled with push protection; a detected secret is rotated, not deleted from history |
| Code scanning | Runs on push and on a schedule; findings triaged like bugs, with an owner |
| Release automation | Tag drives changelog, artifacts and provenance; the release is reproducible from the tag |
| Scheduled audit | Branch hygiene, stale PRs, expiring tokens, unused deploy keys, repos without protection |
| Generated artifacts | Regenerate in CI and fail on drift, so tables and counts cannot rot |

## Repository hygiene

- README answers: what it is, who it is for, how to run it in one command, where the docs are.
- No binaries, no build output, no datasets in git. Artifacts live in a registry or object storage.
- No secrets, ever, and no "temporary" secret in a branch that a future contributor will copy.
- `.gitignore` covers what tooling generates; generated files that must be committed are marked and
  regenerated by a check.
- Tags are annotated and immutable; a released tag is never moved.
- Delete merged branches; keep the default branch deployable at all times.
- One repository, one purpose. A repository that holds the app, the infra and the docs has no
  meaningful review boundary.

## Monorepo or polyrepo

| Signal | Choose |
| --- | --- |
| One team, shared release cadence, atomic cross-package changes | Monorepo |
| Independent release cadence, separate owners, external consumers | Polyrepo |
| Heavy CI cost per change | Monorepo with affected-only builds, else polyrepo |
| Contract between parts that must not drift | Monorepo, or polyrepo with a published, versioned contract |

Whichever you pick, name the source of truth for versions and for the shared contract, and automate the
check that keeps them equal.

## Access and credentials

- Enforce 2FA org-wide; prefer SSO with SCIM so offboarding is automatic.
- Team-based permissions with least privilege; nobody needs admin to review a pull request.
- Automation uses short-lived OIDC credentials, not a personal access token with broad scopes. Where a
  token is unavoidable: fine-grained, expiring, one per integration, documented.
- Default `GITHUB_TOKEN` permissions read-only; elevate per job and per need.
- Review deploy keys and integrations quarterly; revoke what nothing references.
- Stream or export the audit log if the plan allows it; retention is bounded by plan, not by wish.

## Monthly audit checklist

- [ ] Default branch protected; required checks still exist and still pass
- [ ] `CODEOWNERS` paths current; ownership maps to people still on the team
- [ ] Open PRs: every one has an owner, a status and a next action
- [ ] Dependency, secret and code scanning enabled and triaged
- [ ] Branches: stale ones deleted, force-pushed ones explained
- [ ] Credentials: tokens expiring, deploy keys referenced, OIDC preferred everywhere
- [ ] Release: last tag reproducible, changelog matches the diff, provenance present
- [ ] Docs: quickstart still runs verbatim; the commands in the README are not aspirational
